# LocalTTS 음성 품질·안정성 개선 종합 보고서

작성자: **JW-292**  
최종판: **LocalTTS v4.4**  
작성일: 2026-09-01

## 1. 최종 결론

LocalTTS는 배치 파일과 브라우저 의존형 시제품에서 시작해, WinForms 채팅 입력·PIP,
본인 모니터링, Discord 마이크 릴레이, GPT-SoVITS 기반 음성, 비정상 출력 차단,
단일 48kHz float 송출 버스를 갖춘 로컬 앱으로 발전했다.

최종 v4.4는 v4.3의 4화자 조화 모델과 안정장치를 그대로 보존하면서 저중역 마스킹을
0.75dB 단위의 미세 파형 보정으로 줄였다. 25문장 ASR 정확도와 시간축은 v4.3과
동일하게 유지했고, 자음 존재감과 스펙트럼 중심만 개선했다. 모델을 더 크게 만들거나
추가 신경망을 상주시킨 것이 아니므로 GPU 메모리 증가는 없고, 5.38초 WAV의 CPU
후처리는 평균 6.19ms였다.

## 2. 평가 원칙

한두 문장의 인상만으로 운영 모델을 교체하지 않았다. 다음 축을 함께 검사했다.

- 발음: Whisper 기반 문자 오류율(CER), 정확 일치 문장, 문장별 최대 오류
- 시간: 전체 길이, 내부 장무음, 입력 길이에 비해 비정상적으로 긴 출력
- 파형: RMS, near-silence, 급격한 샘플 변화, clipping, spectral centroid
- 음색: 750Hz 저중역, 2~4.5kHz 자음 presence, 비음/자음 에너지 비
- 안정성: 여러 seed, 반복 합성, 서버 재기동, 장치 재열기
- 자원: 모델 크기, Working Set, Private Memory, GPU 메모리, 정상/실패 합성 횟수

운영 적용 조건은 평균 개선뿐 아니라 문장별 회귀, 없는 감탄사, 반복, 장무음,
클리핑이 없어야 한다는 보수적 기준이었다.

## 3. 발전 과정과 문제 해결

### 3.1 실행 구조와 로컬 UI

초기 `run` 배치 파일은 인코딩/경로 문제로 “배치 파일이 아닙니다”와 유사한 오류를
내고 창이 닫혔다. 실행 폴더를 `%~dp0`로 고정하고, 빌드 실패 시 창을 유지하며,
브라우저 대신 WinForms 실행 파일을 만들었다. 채팅을 Enter로 합성하고 접수된 글은
즉시 지우도록 했으며, PIP는 한 줄 입력만 남기고 X를 누르면 종료 대신 본창으로
돌아가도록 정리했다. 브라우저 프로세스를 제거해 게임 중 메모리 변동도 줄였다.

### 3.2 본인 청취와 Discord 송출

TTS를 가상 케이블에만 보내면 사용자는 합성 여부를 알 수 없었다. 한 번 만든 WAV를
모니터 장치와 Discord 장치에 동시에 재생하도록 분기했다. 실제 마이크는 Discord
경로에만 넣어 지연된 자기 목소리가 모니터로 돌아오지 않게 했다.

초기 송출은 마이크와 각 TTS가 같은 VB-CABLE 장치를 별도 `WaveOutEvent`로 열어
경쟁했고, 44.1/48kHz 변환까지 겹쳐 음절 누락이 생겼다. 이를 장치당 하나의 장기 실행
`WasapiOut` shared-mode 버스로 합치고, 장치 기본값과 같은 48kHz stereo IEEE float로
통일했다. 정상 endpoint는 발화 후 유지하고 실제 중단 때만 재생성한다. 한 발화가
끝날 때까지 다음 발화를 막고 Discord gain은 100% 이하로 제한했다.

첫 발화 뒤 이후 음성이 웅얼거리거나 사라진 문제는 매 문장 endpoint를 닫고 다시 여는
회귀가 직접 원인이었다. 장기 endpoint 재사용으로 수정한 뒤 비무음 신호 30회,
동시 입력 8개, 재열기 8회를 통과했다.

### 3.3 Discord Studio에서만 정상인 현상

Studio/순수 오디오에서 정상이라는 A/B는 `TTS → 앱 → VB-CABLE → Discord 입력`까지
신호가 정상임을 뜻한다. 일반 입력 프로필의 Krisp, echo cancellation, AGC, voice
activity gate가 깨끗한 디지털 합성음을 비음성으로 오판해 작은 자음과 모음을 제거한
것이었다. 따라서 가상 케이블 TTS에는 Studio가 자연스러운 운영 설정이다. Studio를
쓰지 않을 경우 모든 후처리와 자동 감도를 끄고 Standard/Legacy subsystem을 비교한다.

### 3.4 Mashiro 기준 음성의 발음 개선

주요 증상은 `ㅇ` 밀집/연음에서 급하게 삼키는 발음, 띄어쓰기 민감성, 문장에 없는
“하/아” 삽입, 구간 경계의 지지직이었다. 다음 개선이 운영 경로에 남았다.

| 문제 | 데이터 분석 | 채택 해결 |
|---|---|---|
| 띄어쓰기 | 잘못 분리된 조사에서 phoneme 경계 변화 | Unicode/공백 정규화와 명백한 조사만 결합 |
| 급발음 | 입력 대비 길이가 짧은 표본과 ㅇ/연음 문장 | 기본 속도 0.94, 짧은 결과 품질 검사 |
| 없는 감탄사/반복 | 높은 무작위성과 특정 seed에서 의미 토큰 폭주 | 낮은 randomness, 정상 seed와 제한된 fallback |
| 긴 문장 특정 구간 붕괴 | 전체 재합성보다 구간별 실패가 관찰됨 | 긴 문장만 문장부호/단어 경계로 분할 |
| 경계 지지직 | 결합점과 고립 샘플 jump 검출 | 12ms fade, 18ms 간격, micro-declick |
| 엔진 비정상 종료 | 서버/캐시/포트 상태 로그 | 자산 사전검사, 300초, 2회 기동, 1회 자동 복구 |

출력 micro-declick은 기존 WAV 46개에서 클릭 검출을 73→63으로 줄였고, 실제 수리된
5파일의 CER은 8.18%로 동일했다. C# 구현은 파일당 2~4샘플만 바꾸고 첫 JIT 이후
약 4.2~5.2ms가 걸려 추가 RAM/VRAM 없이 채택됐다.

### 3.5 학습 데이터와 부분 미세학습

세 유튜브 영상 약 4.55시간에서 2,216개 구간을 만들고, Whisper-small 대조 CER 18%
이하 785개(40.61분)를 선별했다. 사용자가 30개 자막을 직접 검수했으며 유효 28개를
3회 노출해 839행 학습 구성을 만들었다.

| 후보 | 방법 | 결과 | 판정 |
|---|---|---|---|
| candidate v3 | 2,216개, 번들 학습률 | CER 18.86~20.28%, 기준 7.02% | 탈락 |
| v3c | 785개, 저학습률 | 1회 476.16% 반복 붕괴, 2회 25.52% | 탈락 |
| v4 | GPT 마지막 2층, 8.12% 파라미터 | 10.80→11.26%, `ㅇ` 악화 | 탈락 |
| v5 | 마지막 1층, 4.06% | 대부분 기준과 동일 | 보류 |
| v5b | 마지막 1층, 교정자료 강화 | 23문장 8.34→8.11%, 최대 26.32→21.05% | 안정 컨트롤러로 채택 |
| v8 | 마지막 4층+head, 13.1M/77.6M | 고정 seed 10.19→10.02%지만 5-seed 11.70→93.48% | 폐기 |

핵심 교훈은 작은 고정-seed 개선이 일반화 개선을 의미하지 않는다는 것이다. v8은 한
조건에서는 좋아 보였으나 seed를 넓히자 반복 발성이 폭증했다. 따라서 이후 실험은
짧은 선별 → 독립 문장 → 다중 seed 순으로 중단 기준을 두었다.

### 3.6 Reference, G2P, seed 실험

Full reference는 일부 문장을 개선했지만 64.06초 출력과 94.6% 무음을 만들었다.
원본 reference의 68샘플만 보간한 micro-declick도 독립 9문장에서 CER 4.38→4.06%였지만
5문장×5 seed에서 양쪽 6.63%, 클릭 46으로 동률이라 미적용했다.

선택적 G2P는 21문장 중 실제 phoneme가 바뀐 2문장만 소폭 변화했으나, 검수 자료
785개에서 차이가 난 7개를 확대 평가하자 평균 CER이 15.24→25.02%로 악화했다.
고정 seed 404도 첫 세트에서는 12.83→8.08%였지만 독립 세트에서 4.38→8.77%로
뒤집혔다. reference/G2P/seed는 국소 이득이 반복 검증되지 않아 운영 경로에서 제외했다.

## 4. 독립 4화자 모델 v4.2~v4.4

### 4.1 v4.2: 화자 조화

Mashiro를 완전히 배제한 초기 독립 음성은 개성이 약하거나 코먹은 음색이 두드러졌다.
화자별 학습량 차이를 없애기 위해 체크포인트 단순 평균 대신 모듈별 task vector를
정규화했다. 25/25/25/25, 40/20/20/20, Mashiro 50/55%를 비교해
Mashiro/Riko/Tabi/Uni = 40/20/20/20을 선택했다.

| v4.2 후보 | 평균 CER | 최대 CER | no-filler |
|---|---:|---:|---:|
| 이전 v4.1, 0/20/50/30 | 7.15% | 31.58% | 시간축 실패 |
| 균등 25/25/25/25 | 7.00% | 30.43% | 0% |
| **선택 40/20/20/20** | **4.88%** | **21.74%** | **0%** |
| Mashiro 50% | 7.25% | 26.09% | 0% |
| Mashiro 55% | 7.05% | 26.32% | 0% |

`no_filler`의 “아~~~”와 1.24초 내부 공백은 SoVITS보다 GPT 의미 토큰 문제였다.
v5b GPT, seed 24680, top-k 3을 적용해 7.00초 출력을 3.16초로, 최장 내부 공백을
0.06초로 줄이고 ASR 정확 일치를 얻었다. top-k 1~2는 오히려 “아/으” 반복을 만들었다.

### 4.2 v4.3: 재생 전 폭주 차단

8문장에서는 안전했던 seed 24680이 25문장 확장 시 한 문장에서 47.04초 반복과 CER
100%를 만들었다. 완성 WAV를 재생 전에 버퍼링하고 `max(6.5초, 글자 수×0.30초)`를
넘으면 폐기한 뒤 seed 101로 단 한 번 재합성했다.

| 지표 | v4.2 | v4.3 |
|---|---:|---:|
| 25문장 평균 CER | 14.19% | **10.61%** |
| 최대 CER | 100% | **33.33%** |
| 최대 출력 길이 | 47.04초 | **7.20초** |
| 정확 일치 | 8/25 | 8/25 |
| no-filler / clipping | 0% / 0% | 0% / 0% |

정상 문장은 합성 1회로 자원 사용이 같고 실패할 때만 최대 1회 추가한다. 모델 적재 후
측정값은 Working Set 약 1,604.8MB, Private Memory 약 3,291.9MB, 전체 GPU 메모리
약 1,167/6,144MB였으며, 버퍼 WAV는 약 0.2~0.25MB였다.

### 4.3 v4.4: 파형 기반 비음 마스킹 감소

다른 task-vector 비율은 전체 CER을 9.64%까지 낮춘 경우도 있었지만 연음과 `ㅇ` 문장을
악화시키거나 없는 “하”를 재발시켰다. 모델 비율을 바꾸지 않고 완성 파형에 다음의
미세 보정만 적용했다.

- 750Hz, Q 0.8, -0.75dB: 답답한 저중역 공명 완화
- 2,800Hz, Q 0.8, +0.75dB: 자음 윤곽 복원
- 양방향 zero-phase biquad와 peak 0.95 안전 상한

| 파형 지표 | v4.3 | v4.4 | 변화 |
|---|---:|---:|---:|
| spectral centroid | 878.30Hz | 964.92Hz | +9.9% |
| 비음/자음 에너지 비 | 7.59dB | 5.98dB | -1.61dB |
| 2~4.5kHz presence | 6.342% | 9.080% | +2.738%p |
| clipping | 0% | 0% | 동일 |
| 25문장 평균/최대 CER | 10.61/33.33% | 10.61/33.33% | 동일 |

±1.5~2.5dB의 강한 EQ는 밝고 얇아지며 일부 ASR/no-filler를 악화시켜 폐기했다.
v4.4는 생성 음소와 타이밍은 바꾸지 않고 마스킹만 줄인 안전한 최종점이다.

## 5. 자원과 게임 병행 관점

모델 추론 부하는 앱이 처음 음성을 부를 때만이 아니라 **채팅을 입력해 합성할 때마다**
발생한다. 다만 모델은 첫 호출 후 메모리에 유지되므로 매 문장 재로딩은 하지 않는다.
대기 중 앱 UI는 가볍지만 엔진의 RAM/VRAM은 상주한다. Python은 `BelowNormal` 우선순위로
실행해 게임 스레드 우선권을 보존한다.

SSD와 HDD에 페이지 파일을 동시에 둘 수 있지만, 페이지 파일은 느린 RAM 대체이며
GPU VRAM 부족이나 전원/온도 문제를 해결하지 않는다. 게임이 전체 자원을 80~90%
사용한다면 합성 순간 frame-time spike가 생길 수 있다. 안전 운영은 SSD 페이지 파일을
시스템 관리로 유지하고, VS Code/브라우저를 닫고, 게임 VRAM 여유를 약 1.2GB 이상
확보하며, TTS 문장을 연속으로 겹치지 않는 것이다. 자동 재부팅은 보통 단순 CPU 100%
보다 전원·온도·드라이버·메모리 불안정 가능성을 먼저 점검한다.

## 6. 적용하지 않은 주요 방법

| 방법 | 탈락 이유 |
|---|---|
| 저자원 모드 매회 unload | 실행 대기가 길고 재로딩 비용이 더 큼 |
| 무조건 고품질/강한 후처리 | 음색·자연스러움 저하, 자원 증가 |
| Full reference/multi-reference | 장무음·폭주·자음 presence 저하 |
| 전체/선택 G2P | 확대 세트 CER 악화 |
| 강한 EQ/denoise | 발음 단서와 자연스러움 손실 |
| v8 부분 파인튜닝 | 다중 seed에서 반복 붕괴 |
| 공격적 속도 저하 | 일부 CER 개선과 다른 문장/클릭 회귀 동반 |
| 로컬 rush detector | 민감도 30.3%, balanced accuracy 61.7% |
| RMS/ZCR 반복 detector 단독 | Whisper 환각과 실제 반복을 혼동할 오탐 위험 |

## 7. 최종 앱의 안전 설계

- 기존 `LocalTTS.exe`와 모델은 덮어쓰지 않는 별도 `LocalTTS_v4.4.exe`
- 별도 mutex와 API 포트 9884로 구버전 충돌 방지
- 모델·reference SHA-256 고정 및 시작 전 존재/크기 검사
- 앱 내부 전용 YAML을 매 기동 현재 설치 경로로 생성해 공용 설정 오염 방지
- 앱 옆 `cache/numba`를 사용해 AppData ACL/임시파일 재시도 문제 방지
- Python stdout/stderr를 안정성 로그에 기록해 갑작스런 실패 원인 보존
- 서버 300초 준비창, 2회 기동, 합성 중 소실 시 동일 시도 1회 복구
- 정상 WASAPI endpoint 유지, 장애 때만 재생성
- 한 발화씩 순차 처리, 출력 gain 100% 상한

## 8. 최종 운영 절차

1. `run_v44.bat`을 실행한다.
2. Discord 출력은 `CABLE Input`, 모니터 출력은 실제 헤드폰/스피커로 둔다.
3. Discord 입력은 `CABLE Output`, 입력 프로필은 Studio/순수 오디오로 둔다.
4. 첫 문장은 엔진 준비 때문에 더 오래 걸릴 수 있다.
5. 이후 PIP에서 Enter로 한 문장씩 보낸다.
6. 문제가 생기면 `LocalTTS_stability.log`와 세 자체 검사 종료 코드를 확인한다.

## 9. 최종 판정

v4.4는 새로운 대형 모델이나 과도한 후처리 대신, 검증된 4화자 음색층·v5b 운율
컨트롤러·1회 폭주 복구·미세 파형 보정을 결합했다. 발음 CER와 no-filler 안정성을
희생하지 않고 코먹은 저중역 마스킹을 줄였으며, 현재 PC에서 실제 엔진 종단 합성과
Discord 버스 반복 검사를 통과했다. 따라서 이 폴더의 `LocalTTS_v4.4.exe`를 최종
독립 실행판으로 판정한다.
